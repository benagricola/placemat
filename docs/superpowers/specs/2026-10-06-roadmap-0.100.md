# Roadmap to 1.0: phases, one score, refine, the loop

Status: draft for review, 2026-10-06. This is the overarching plan for the four 2026-10-06 designs, on the 0.100.x
release line; the user cuts 1.0 once all of it is merged.

## Why

On the fairing core, placemat got a complex board to about 90% routed, but the last stretch stalled for four reasons:

- **Slow judgement:** each placement change cost a full resolve, and each explore variant cost minutes.
- **A frozen board:** locks pinned whatever an explore once chose.
- **Five objectives:** placements were made against one score and judged by another.
- **Declared power legs:** declared copper over-constrained placement, and routing had no order the project controlled.

Agents also had to know a long sequence of commands, and acted only on findings that changed the board.

The work replaces that with one loop: place, refine, route the phases, score, refine again. It uses one score and runs
as one command, and the script's and the capture's constraints are the only things that hold an item.

## The designs and their order

| # | Design | Spec | Depends on | Ships alone? |
|---|---|---|---|---|
| 0 | The reference set: manifest, fetch script, each board's capture and minimal layout script, and a runner for tests (a) and (b) that records results per release | this roadmap, "The reference set" | none | yes: it measures today's placemat as the baseline |
| 1 | Routing phases | 2026-10-06-routing-phases-design.md | the KRT fork (`--connections`), the Zener fork (`nets.layout.json`) | yes: phases replace the fixed stages |
| 2 | One score | 2026-10-06-one-score-design.md | none | yes: the search, the turn check and explore move onto one score, behind its gate |
| 3 | Refine | 2026-10-06-refine-pass-design.md | 2 | yes: coarse and fine refine inside `run`, the snapshot in place of the lock |
| 4 | The loop | 2026-10-06-place-route-loop-design.md | 1, 2, 3 | yes: `run` becomes the loop, the skill teaches one command |

0 comes first, so the baseline is recorded before anything changes. 1 and 2 are independent and can be built side by
side. Each is released as it lands, as 0.100.0 and then 0.100.y.

## Work outside placemat

- **KRT fork** (benagricola/KiCadRoutingTools): the `--connections` option routes only given pad pairs, at a width per
  layer. A flag routes a stated group of nets as one bus, if detection misses it. Each change gets its own tests in
  KRT's suite and is pushed to the fork.
- **Zener fork** (benagricola/pcb): `nets.layout.json` written beside the board. It holds each net's type and fields,
  its interface instances, its `DiffPair` membership and a `clearance` field on the stdlib net types. Stage 1 is types
  and fields; stage 2 is interfaces. The board venvs need a pcb build with it before phases can select by interface.

- **The circuit-capture skill** (~/work/circuit-capture, its own repo and charter) changes in step 1, with the
  Zener fork's net export:
  - a bus is a stdlib interface, and that alone reaches the board: no `NetClass` per bus;
  - a differential pair is a `DiffPair` instance;
  - a net's electrical clearance is its `clearance` field;
  - net classes keep width, clearance and impedance only;
  - its "Where a fact lives" table and "A net-level fact with no class does not reach the board" are rewritten to
    match.
- **The placemat skill** changes in every step, with each form the step adds or removes (the removal ledger).

## The reference set

Interim steps are measured against boards people have already placed and routed, not against the fairing core alone.
The core has no finished placement: on it an interim change can only be compared with placemat's earlier output, and a
worse step could pass for progress.

**Boards** (scratchpad/corpus/REPORT.md; each pinned to a commit, licence recorded):

| Board | Parts | Layers | Licence |
|---|---|---|---|
| pic_programmer (KiCad demo) | 63 | 2 | CC-BY-SA-4.0 |
| usb-c-power-adapter (antmicro) | 122 | 4 | Apache-2.0 |
| LoRa-V3 | 84 | 2 | MIT |
| ir-irradiance-probe (antmicro) | 57 | 2 | Apache-2.0 |
| esp-rust-board | 55 | 2 | CERN-OHL-P-2.0 |
| Watchy | 84 | 4 | MIT |
| spimux (oxide) | 22 | 2 | MPL-2.0 |
| chainlinkDriver (splitflap) | 65 | 2 | Apache-2.0 |

ESP-PROG is optional, for continuity with KRT's tests.

**Storage:** a committed manifest holds, per board:
- the repo, the commit, and each file's sha256;
- the SPDX licence;
- the board's facts: its nets for phases, its fixed parts, and its pre-route DRC baseline.

A fetch script writes the boards to a git-ignored cache. The boards are not vendored.

**Test (a), route the human placement:**
1. Strip the copper, keeping the zone definitions.
2. Record the stripped board's DRC as the baseline: several originals already fail DRC once stripped.
3. Route with the board's own layer count, net-class rules and via sizes.

Pass is 100% clean closure, with no copper DRC error beyond the baseline. Closure is also recorded at the widths the
human actually used, so a gap caused by width alone is visible (decided with the user). Vias and track length are
compared with the human board.

**Test (b), place and route:**
1. The board's mechanical parts (connectors, holes, edge parts) are held where the original put them, from the manifest.
   This is allowed for the reference set only (decided with the user); a real board's script never states coordinates.
2. placemat places everything else and routes it.
3. The result is compared with the human board, and with placemat's own test (a) route of the human placement. That
   second comparison separates placement quality from routing quality.

Test (b) needs the board in placemat's flow. Only 2 of 9 import today with `pcb import`. The rest fail on field and
net-name drift, mounting-pad pins, or KiCad 5 schematics, and fixing those is Zener-fork work. Until then, test (b) runs
on the boards that import, and test (a) runs on all of them.

**Starting small** (decided with the user). Writing and validating a capture and a layout script per board, with its
datasheets, takes long and is easy to get wrong, and a wrong set would blame placemat for the data's faults. So:
- **Test (a) runs on all eight open boards.** It needs no capture or script: it routes the human placement as it
  stands.
- **Test (b) starts with two open boards** that import today:
  - pic_programmer: DRC-clean original, 2 layers, through-hole;
  - usb-c-power-adapter: 4 layers, power and USB; its reference is the regenerated board, because the import swaps
    footprints.

  A third, likely LoRa-V3 once the Zener fork fixes its mounting-pad import, is added only after these two have shown
  the process works.
- **Our own modules carry most of test (b):** their captures and scripts already exist and were checked in the board
  work. The fairing modules with hand-adjusted placements (`hand/`, 11 modules) give a placement to compare against.
  The bench modules are judged by the module order: 100% routed, then area.

**Writing each board's capture and layout script.** The reference boards have no placemat scripts. Step 0 writes, for
each board:
- a Zener capture: from `pcb import`, plus the annotations a circuit designer would add from the datasheets (`Pm.I`
  on parts that carry current, roles, sensitivities, sources, pin pools where the part allows swaps), following
  capture.md;
- a placemat layout script, following SKILL.md and api.md.

The agent that writes them loads three things: the human board (to read what the designer fixed), the capture, and
both skills: the placemat (layout) skill, and the circuit-capture skill
(~/work/circuit-capture/skills/circuit-capture, Zener-specific: where each fact lives, buses, modules for placement,
sourced numbers). It works as a layout engineer would, from mechanical facts and the circuit.

**The rules for a reference script.** A reference script is as simple as the board allows, so the set measures
placemat rather than the quirks of a script.
- **Fixed parts:** only those a human layout engineer fixes for mechanical reasons. These are connectors, mounting
  holes, switches and buttons, displays, LEDs at enclosure windows, antennas and their keepouts, and edge parts. They
  are held at the human board's coordinates, which is allowed for the reference set only (decided with the user).
- **Everything else is intent:** relations from the circuit (a bypass capacitor at its pin, a crystal at its MCU, a
  link with a worked number), or searched. Each declaration has a `why=` naming its basis: mechanical, datasheet or
  physics. No steering: no priority, order, `Near` or link added to improve a result.
- **Routing phases:** the default set from `placemat settings --example`, plus only phases the capture's interfaces and currents
  call for.
- **A check:** a script lint in the runner lists every declaration by its basis. A reviewer checks each new or changed
  reference script against these rules before it is accepted.

**Keeping them current.**
- **Like test fixtures:** the reference scripts and captures live in the placemat repo with the manifest. Every step
  that removes or changes a form (the removal ledger) migrates them in the same change. A step whose migration breaks
  them is not done.
- **Only for migration or a real error:** a script changes for a migration, or to fix a constraint that is wrong about
  the board. It never changes to improve a score. Each change is reviewed against the rules above, and the result
  before and after is recorded.
- **Skill gaps:** where either skill led the writing agent wrong, or a needed form was missing, the skill is fixed
  (placemat's in this repo, circuit-capture's in its own repo under its charter), not the script worked round. Writing
  the set tests both skills as much as the engine.

**Modules.** Fitted modules are judged by the module order: 100% routed, then area. The fairing modules with
hand-adjusted placements (`hand/`, 11 modules) serve as placement references.

**Ratchet.** Each step's release records the set's results. A step may not make any reference board's test (a) or (b)
result worse without the user's approval.

## Gates

Each gate is measured before the step it guards is adopted. A failed gate sends the design back to the user with the
numbers.

- **One score:** the search's switch from the clique to the MST change must leave no bench fixture's run score worse,
  and no reference board's test (b) result worse. A candidate must stay under about 5 us natively.
- **Refine, speed:** a prototype reaches 2,000 moves a second on the core before the full build. The target is 10,000.
- **Refine, result:** the bench in three configurations shows no fixture worse, and the reference set's test (b)
  improves or holds.
- **The loop:** the reference set's test (b) reaches 100% clean closure on the boards whose humans did. The fairing
  core is reported beside it, as a secondary measure.

## Removal ledger

Everything these designs supersede, the step that removes it, and what replaces it. Nothing here stays behind as a
second way of doing the same thing. Each item is removed in the step that replaces it, never later. Its plan's last task
deletes the code, the tests, the settings, the CLI options and the docs, and adds a migration entry that tells a script
or a `placemat.toml` what to write instead.

| Removed | In step | Replaced by |
|---|---|---|
| Fixed route stages (pairs, islands, classes, main) and their names | 1 | named phases |
| `[route] islands`, `[route] pair_layers`, `route --islands` | 1 | phase `nets` or `connections` with `width`; `pairs = true` with `layers` |
| `[route] net_halos` | 1 | the capture's net `clearance` field |
| Pairs derived from net-class patterns (`pairs.board_pair_list` for selection) | 1 | `DiffPair` instances from `nets.layout.json` |
| The search's own crossing estimate and clique wire in `Scorer`, if the gate passes | 2 | the run score's incremental terms |
| turn.better's own wire and crossing terms | 2 | the run score's incremental change |
| Explore's added congestion term | 2 | congestion as a run-score term |
| The pin study's own crossing weights | 2 | `[score]` weights by net kind |
| Cleanup pass (`cleanup.py`, `_cleanup`, `PartScore`, `NativeCleanupScoring`) and `[cleanup]` settings | 3 | refine |
| Lock (`lock.py`, `<stem>.lock.json`, `placemat lock` and subcommands, `lock --current`, `lock --accept-seed`) | 3 | the snapshot (`<stem>.placement.json`), constraints in the script |
| `freeze` | 3 | constraints in the script |
| `route --adopt` locking the items it joins | 3 | none: kept routes stay, nothing is locked |
| `board.alternative`, `board.unit`, arrangement alternatives, `place.arrangements_max` | 3 | refine of cell members |
| `--rank-remapped`, `explore.rank_remapped`, and the pin study's separate pose search | 3 | coarse refine owns poses, and the pin study runs inside it |
| turn.better on items refine may move | 3 | refine takes those turns. turn.better stays only for turns the script or a stated constraint owns |
| `preview` | 4 | `run --place-only` |
| `--explore SECONDS`, `--focus*`, `--accept`, `--route-best`, `--route-top` | 4 | `run --restarts N`; ranking by phases |
| The studio's explore and lock views of removed features | 3, 4 | views of restarts and the snapshot |
| SKILL.md's multi-command workflow | 4 | one loop: constraints, phases, `run --detach`, `watch --summary` |
| circuit-capture skill: a `NetClass` per bus, pairs by `*_P`/`*_N` class patterns, net facts only through classes | 1 | interfaces, `DiffPair`, net types and the `clearance` field, exported by the Zener fork |

What is kept: suggestions, `apply` and `check`; the studio as a viewer; `route --phase` for routing one phase; and
`route --adopt` for keeping copper on purpose.

## Keeping dead code out

1. **The ledger is the checklist.** Each plan ends with a "Remove" task that names its ledger rows. The final review of
   each step checks every row it owns against the code. Each `grep` for a removed name (`lock_digest`, `cleanup`,
   `alternative`, `--explore`, ...) must return only migration notes.
2. **A CLI surface test.** One test lists every command and option `placemat --help` exposes. A removed one must be
   absent, and a new one must be added to the list on purpose.
3. **A settings surface test.** It does the same for every `[section] key` the settings accept. The generated
   settings table is compared against it.
4. **Unused-code check per release:**
   - Python: an unused-code check (vulture, with a short allow list of entry points), run in CI and on every release;
   - Rust: `cargo build` with `-D dead_code` on the native module.

   A finding is fixed or justified in the allow list with a reason.
5. **Docs follow code.**
   - api.md, SKILL.md, capture.md and the migration notes are updated in the same commit as each removal.
   - A docs test checks that no reference doc names a removed command, option or setting outside the migration notes.
6. **No deprecation period.** Placemat's users are the board sessions, and each release notice says what to migrate. A
   removed form is refused with a message naming its replacement, never kept working alongside the new one. That is the
   project's existing rule.

## Release line

- 0.99.x continues for fixes until the first of these lands.
- Each step ships as 0.100.y with the full suite, the bench, a migration section and a release notice to the board
  sessions.
- 1.0 is cut with the user after step 4 and the last ledger row are merged.
